## 1. 問題

012 修好「只憑 session 不能設定密碼」之後重跑探測，發現**只拿到一個被竊的 session**，仍有三條路可以永久接管帳號：

| 路徑 | 受害帳號 | 手法 | 為什麼特別糟 |
|---|---|---|---|
| A | Google SSO-only | 把攻擊者的 LINE 綁上去 | 綁定的身分改密碼撤不掉、登出全部裝置也撤不掉；原本也**沒有解綁端點** |
| B | SSO-only、只有手機 | 加上攻擊者的 email → 設定密碼的驗證碼寄到攻擊者那裡 | 驗證碼優先寄 email |
| C | 有密碼、只有手機 | 加上攻擊者的 email → 用它走忘記密碼 | session 只要用一次，之後隨時都能重設 |

根本原因相同：**規則只要求「改動既有的東西」出示證明，「新增」不用**。但對攻擊者來說，新增一個登入方式或救援管道，跟換掉一個一樣有價值。

## 2. 使用者

| 角色 | 需求 |
|---|---|
| 帳號擁有者 | 綁定或解綁 Google/LINE；有東西被加上去時要知道，而且要拿得掉 |
| 攻擊者（只有被竊 session） | 應該什麼都做不了 |

## 3. 使用者故事

### US-1 綁定第三方登入需要證明（P1）

身為帳號擁有者，我想綁定 LINE；別人拿到我的 session 時則不能綁他自己的。

**驗收條件**
1. **Given** 只有 session，**When** 呼叫 `POST /auth/link/line`，**Then** 回 422 `step_up_required`，而且**沒有**綁定任何東西。
2. **Given** 有密碼的帳號，**When** 帶正確密碼綁定，**Then** 回 200。
3. **Given** 帶錯密碼，**Then** 回 401 `step_up_invalid`。
4. **Given** 這個 LINE 已經綁在別的帳號，或本帳號已經有 LINE，**Then** 直接回 409，**不會**先要求證明（ADR-217）。
5. **Given** 綁定成功，**Then** 帳號每個聯絡方式都收到通知。

### US-2 解綁第三方登入（P1）

身為帳號擁有者，我在 `/users/me` 看到一個不是我綁的 LINE，我要能把它拿掉，而且透過它登入的人要被踢出去。

**驗收條件**
1. **When** 呼叫 `DELETE /auth/link/line` 並帶證明，**Then** 回 204、**所有 session 被撤銷**（ADR-236）、每個聯絡方式都收到通知。
2. **Given** 沒帶證明，**Then** 回 422。
3. **Given** 移除後帳號沒有其他 SSO，也沒有設定過的密碼（聯絡方式不算登入方式），**Then** 回 409 `last_login_method`，而且不要求證明、不寄任何信。
4. **Given** 帳號沒有綁這個 provider，**Then** 回 404 `sso_not_linked`；provider 名稱不認得，回 404 `sso_provider_unknown`。
5. **Given** 兩個解綁請求同時送出（google 和 line 各一個），**Then** 至少有一個被拒，帳號不會變成沒有登入方式（ADR-235）。

### US-3 新增聯絡方式需要證明（P1）

**驗收條件**（ADR-220 / 234，推翻 012 的 ADR-086）
1. **Given** 有密碼、只有手機的帳號，**When** 只憑 session 加 email，**Then** 回 422，攻擊者的 email **收不到**驗證碼，路徑 C 無法完成。
2. **Given** SSO-only、只有手機的帳號，**When** 加 email，**Then** 驗證碼寄到**既有的手機**。
3. **Given** 只有 LINE、沒有聯絡方式也沒有密碼的帳號，**When** 加 email，**Then** 要出示**這個帳號自己的** LINE `id_token`；攻擊者自己的 LINE token 回 401。
4. **Given** 完全沒有任何東西可以證明的帳號，**Then** 可以直接新增（沒有東西可偷）。

### US-4 剛加入的聯絡方式不能拿來證明身分（P2）

**驗收條件**（ADR-219）
1. **Given** 帳號有一個滿 7 天的手機和一個 3 分鐘前加的 email，**When** 需要寄驗證碼，**Then** 寄到手機（即使一般情況下優先 email）。
2. **Given** 全新帳號，唯一的聯絡方式未滿 7 天，**Then** 仍然可以用它證明（退回用最舊的那個）。
3. **邊界**：加入時間與現在相差**大於或等於** 7×24 小時，就算已過冷卻期（`now - created_at >= 7 days`，UTC）。

### US-5 改密碼要通知（P3）

**驗收條件**
1. **When** `change-password` 成功，**Then** 帳號每個聯絡方式都收到通知。

## 4. 功能需求

- **FR-001**：任何會讓帳號多出一個永久進入方式的操作（綁 SSO、新增聯絡方式、設定第一組密碼），都必須證明持有這個帳號。
- **FR-002**：證明依序為：密碼 → 已過冷卻期的聯絡方式收碼 → 帳號自己已綁定的 SSO 重新驗證。
- **FR-003**：用來收驗證碼的聯絡方式必須已加入滿 7 天；若全部都未滿，使用最舊的。
- **FR-004**：解綁要出示與綁定相同的證明，並撤銷所有 session。
- **FR-005**：帳號必須永遠保留至少一個登入方式（密碼只有在真的有 hash 時才算）。
- **FR-006**：綁定、解綁、改密碼成功後，必須通知帳號每一個聯絡方式。
- **FR-007**：驗證碼綁定動作與目標：`link_identity:google` 的碼不能用在 `link_identity:line`，也不能用在換聯絡方式。
- **FR-008**：衝突檢查（409）必須在要求證明之前。

## 5. 前端契約

| 端點 | Body | 成功 |
|---|---|---|
| `POST /auth/link/google` | `{ id_token, step_up? }` | 200 |
| `POST /auth/link/line` | `{ id_token, step_up? }` | 200 |
| `DELETE /auth/link/{provider}` | `{ step_up? }`（選填 body） | 204，**呼叫者自己的 session 也會失效** |

| HTTP | `code` | 前端應該做什麼 |
|---|---|---|
| 422 | `step_up_required` | 顯示證明欄位，填完用同一顆按鈕重送 |
| 422 | `no_proof_channel` | 「請先新增一個聯絡方式」 |
| 401 | `step_up_invalid` | 「密碼或驗證碼錯誤」 |
| 409 | `sso_already_linked` | 「這個帳號已經綁定過了」 |
| 409 | `last_login_method` | 「至少要保留一個登入方式」 |
| 404 | `sso_not_linked` | 「沒有綁定這個登入方式」 |
| 404 | `sso_provider_unknown` | 程式錯誤（provider 只有 `google` / `line`），不應發生 |

`step_up` 欄位：`password` / `old_channel_code` / `id_token`。證明種類由後端決定，422 的 `detail` 會說明要哪一種。

**對 012 前端的破壞性變更**：新增第二種聯絡方式原本直接 202，現在會先回 422。

## 6. 範圍外

- session 的「最近驗證過」（sudo window）：補強措施，另開票
- Microsoft 式的「變更先進待決狀態、可取消」：對目前階段太重
- 風險引擎、裝置指紋
- 只撤銷透過某個 SSO 取得的 session（session 沒記錄來源；ADR-236）
- 前端表單（ADR-237）

## 7. 成功指標

- **SC-001**：路徑 A、B、C 以及 ADR-234 那條鏈，都有端到端測試斷言「被擋下」，而且全部通過。
- **SC-002**：正常使用者綁定或新增聯絡方式時，只多一步（輸入密碼或驗證碼）。
- **SC-003**：任何登入方式變動，擁有者都能在變動前就存在的管道收到通知。
