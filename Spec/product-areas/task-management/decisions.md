# Task Management binding decisions

Only approved decisions that still constrain product behavior appear here. The complete discussion record is preserved in [decision history](./research/decision-history-2026-08-01.md).

| ID | Decision | Reason | Superseded behavior | Effective Feature | Date |
|---|---|---|---|---|---|
| D4 | Intake supports citizen, staff-assisted, and system-originated paths; citizen intake must not be blocked by specialist fields. | A life-safety report must remain short enough to submit under stress. | A single mandatory-field policy for every intake path. | TM-FEAT-004; boundary for TM-FEAT-001 | 2026-06-16 |
| D7 | Ticket is the location anchor; it owns multiple Tasks, and specialist information may be added later. | Separating location from actionable needs permits independent coordination without lengthening first contact. | Treating a Ticket as one indivisible need. | TM-FEAT-004 and TM-FEAT-002 | 2026-06-16 |
| D9 | Remove the duplicate Ticket-level task category; Task is the category authority. | The Ticket field duplicated Task data and created drift. | Reading category from a Ticket summary field. | TM-FEAT-004 | 2026-08-01 |
| D10 | Task categories remain system-defined; configurable fields attach below a category, and applying a disaster field group only adds fields. | Stable categories preserve coordination semantics while fields provide incident flexibility. | Allowing administrators to create task categories or automatically removing fields with a disaster group. | TM-FEAT-001 | 2026-08-01 |
| D11 | Disaster field groups are product definitions shipped by engineering; administrators may apply but not author them during an incident. | Group design needs domain review outside incident pressure. | Incident-time editing of group composition. | TM-FEAT-001 | 2026-08-01 |
| D12 | When adding a field, search the system field library first and create an incident-local field only when no suitable entry exists. | Stable field identity permits safe reuse and prevents avoidable duplicates. | Unstructured name entry as the only path. | TM-FEAT-001 | 2026-08-01 |
| D13 | An incident-local field has the same filtering, required/optional, and incident-reporting capabilities as a library field; promotion to the library is a later governed action. | A single-incident database removes the rejected cross-incident reporting concern. | Treating local fields as second-class data. | TM-FEAT-001 | 2026-08-01 |
| D14 | Only a Super Admin may change the incident field configuration. | The configuration affects every operational form. | Reusing general map-edit permission for field configuration. | TM-FEAT-001 | 2026-08-01 |
| D15 | A configured field can be deactivated but not deleted; historical values remain readable and the field may be reactivated. | Operators need shorter current forms without orphaning collected evidence. | Deleting field definitions or hiding historical values. | TM-FEAT-001 | 2026-08-01 |
| D16 | A field is required or optional; conditional-required rules are not supported. Guidance may recommend additional information but must not block saving. | Conditional rules add unsafe operational friction and complex interactions. | Conditional-required rule engines and the former three-gate rescue rule. | TM-FEAT-001 | 2026-08-01 |
| D17 | Field identity is a stable ID and the displayed name is a label. Renaming never detaches collected values. | Reuse, deactivation, and later library promotion all require an identity that survives editing. | Treating the field name as its identity. | TM-FEAT-001 | 2026-08-02 |
| D18 | One field identity may attach to several Task categories. Required state and activation belong to the field-category pair, not to the field. | The same real-world detail matters to more than one kind of work, at different levels of obligation. | A field belonging to exactly one category. | TM-FEAT-001 | 2026-08-02 |
| D19 | Configuration changes are not retroactive. A Task is checked against the configuration in force when it was created, an open form completes under the configuration it was opened with, and collected values are never altered or removed by a later change. | Retroactive rules either block work that is already finished or destroy evidence, and both push operators to enter false data. | Applying new configuration to existing Tasks and already-open forms. | TM-FEAT-001 | 2026-08-02 |
| D20 | A required field is enforced when a Task is closed, never when a form is saved. | Field information arrives progressively during an incident; blocking the save loses the report, while blocking closure keeps the record honest. | Enforcing required fields at save time, or giving required state no effect at all. | TM-FEAT-001; the closing actor is owned by TM-FEAT-002 | 2026-08-02 |
| D21 | A field type may be corrected after values exist. Values that do not fit the new type are retained unchanged and marked as non-conforming. | An early wrong type otherwise forces a duplicate field, which D12 exists to prevent. | Locking the type once values exist, or rewriting stored values to fit. | TM-FEAT-001 | 2026-08-02 |
| D22 | Removing a choice from a list field removes it from new entries only; previously selected values stay readable. | Same evidence principle as D15. | Deleting or rewriting values that reference a removed choice. | TM-FEAT-001 | 2026-08-02 |
| D23 | Reactivating a field restores the required state it held when it was deactivated. | Deactivation is a temporary shelf, not a reset; silently returning to optional loses the data the field exists to collect. | Reactivation defaulting to optional. | TM-FEAT-001 | 2026-08-02 |
| D24 | Creating a field warns when a similarly named field already exists but never refuses creation. | Name matching cannot detect meaning, so a hard block would stop legitimate new fields while still missing real duplicates. | Blocking on name similarity, or creating silently with no check. | TM-FEAT-001 | 2026-08-02 |
| D25 | An applied disaster field group can be reverted as one action while none of the fields it introduced holds a value. Once any value exists, only per-field deactivation applies. | A group applied by mistake under time pressure should not leave permanent residue, and an untouched field carries no evidence to protect. | Irreversible group application, or a reversal that discards collected values. | TM-FEAT-001 | 2026-08-02 |
| D26 | Every signed-in user may read the field configuration; only a Super Admin may change it. The guest intake form contains no configurable fields. | A form cannot render without its configuration, while D4 keeps the citizen report short enough to submit under stress. | Restricting configuration reads to Super Admin, or exposing specialist fields on the guest form. | TM-FEAT-001 | 2026-08-02 |
| D27 | A configuration change affects only the fields it names; a whole field list is never written back as one replacement. | Two administrators work at once during an incident, and whole-list writes silently discard the other's change. | Saving the configuration as a complete list. | TM-FEAT-001 | 2026-08-02 |
| D28 | A Task form places required fields above optional fields under a visible separator and does not collapse the optional section. A newly added field is marked until it is first filled. | Closure depends on the required fields, hidden optional fields go unfilled, and marking the new field puts the change where the person filling the form will see it. | Collapsing optional fields behind a control, or announcing configuration changes by broadcast. | TM-FEAT-001 | 2026-08-02 |
| D29 | A Task category with no configured fields is valid and stays fully usable. Which fields a category starts with is product content, not a behavior rule. | Every field is added by someone at some point, so an empty category is the normal starting state rather than a defect; requiring a minimum would block the categories that need the fewest details. | Hiding or disabling a category that holds no configured fields. | TM-FEAT-001 | 2026-08-02 |
| D30 | Medical fields ask the reporter what they can see, never for a clinical classification. The category ships with a casualty count and the condition of the most severely affected person, stated as plain observations with "not sure" always available, plus two optional fields. Every other shipped field starts optional. | The first person on scene is usually an untrained volunteer. Asking for a triage level asks for a conclusion that takes training to reach, which produces either a guess that misdirects dispatch or a report that never gets filed. The observations behind a triage decision need no training, and a trained reader recovers the classification from them. An unknown must be recordable as unknown rather than as a wrong classification. | Requiring the reporter to classify casualties by triage level, or into counts per level. | TM-FEAT-001; professional assessment moves to TM-FEAT-007 | 2026-08-02 |
