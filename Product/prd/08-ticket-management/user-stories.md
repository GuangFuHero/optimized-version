# User Stories — 任務管理 (Ticket Management)

> **根基文件（北極星）。** 先在這裡定義「為誰、在什麼情境、想達成什麼價值」；同資料夾的 `prd.md` 是由本文件**推導出來**的功能規格（如何實作）。閱讀與設計順序：先讀本文件（問題空間），再讀 `prd.md`（解法空間），避免從功能反推需求。
>
> 平台 RBAC 角色的權威定義見 [[04-rbac]]；地圖底圖與劃區指派見 [[06-map-decision-support]]；資源站點見 [[07-resource-station]]；Team 與志工身份見 [[05-member-management]]。本文件只列與「任務管理」直接相關的使用者目標。

---

## 核心模型（一句話北極星）

> **把「現場的求救與需求」變成「可被指派、可被接案、可被追蹤」的任務。**

- **Ticket = 地點錨點**：一個出事的地址（地址、經緯度、現場聯絡人、災害種類）。
- **Task = 需求**：掛在 Ticket 底下的一筆筆具體需求（破拆人力、圓鍬、礦泉水、有人受困…）。一個 Ticket 可有多個 Task。
- **接案以 Task 為單位**：志工承接的是「需求」，不是整個地點。
- 災害種類**繁多**（地震／水災／火災／颱風／土石流／海嘯…），同一套 Ticket→Task 骨架必須能彈性承載所有災種；**災害專屬的專業情報（結構穩定度、受困樓層…）採「報案精簡、後台後補」**，不卡住第一線求救。

## 角色

| 角色 | 在本特性中的立場 |
|------|------------------|
| 一般使用者 / 市民 / 受困者 | 前台自助報案（`citizen_report`）：只填得出最基本的地點與需求 |
| 志工（接案者 actor） | 在承接清單挑選 Task 承接、回報進度；身份模型對齊 [[05-member-management]] |
| Team Member | 後台代報（`staff_intake`，含電話進線）、處理自家被指派的任務 |
| Team Admin | 管理自家責任區的 Ticket/Task、為自家建築啟動專業救援模式 |
| Government | 劃區批次指派任務給 Team；不看 Team 內部名單 |
| Super Admin | 全域：設定災害種類、最高優先級覆寫、刪除任務 |
| Data Auditor | 審查 AI 建議：同地點群組化、疑似重複任務比對 |

## 使用者情境（多災種，凸顯同一骨架的彈性）

> 以下情境共用同一套 Ticket→Task 模型，差別只在 `disaster_type` 與「是否需要後補專業欄位」。

* **地震・有人受困**：花蓮地震，仁愛路 100 號透天厝半倒，1 樓阿姨受困、爸爸困 3 樓。報案只填「地點＋需求（破拆人力、圓鍬、有人受困）」；結構穩定度、受困樓層等**由後台指揮事後補齊**。
* **水災・清淤需求**：仁愛路積水，需要清淤人力與圓鍬。純人力＋物資需求，**沒有任何結構欄位**，報案表單極短。
* **火災・高樓延燒**：大樓 5F 起火向上延燒，需破拆與確認危害物質。屬需要直立救援的災種，後台補結構/危害資訊。
* **颱風・路樹倒塌停電**：路樹壓線、整條街停電，需要交通排除與通訊/電力支援；需求會連動到 [[07-resource-station]] 的發電/通訊站。
* **純物資需求**：避難所礦泉水見底，由站點主責人開一筆「物資-礦泉水 ×200」Task，無關建築。

* **共同痛點 / 觸發點：**
  * 求救當下若用一長串專業必填欄位，會把驚慌中的市民擋在門外。
  * 不同災害需要的資訊差很多，硬塞同一張長表會讓現場填寫崩潰。
  * 一個地點往往有多種需求（人力＋物資＋搜救），混在一筆任務裡無法分別指派與媒合。
  * 同地址多筆報案若不整理，地圖被重疊標點淹沒。

## User Stories（依角色）

### 一般使用者 / 受困者（前台報案）
* As a 受困市民, I want **用極簡表單快速報案（地點＋聯絡方式＋需要什麼）**, so that 在驚慌中也能 30 秒內送出求救，不被專業欄位卡住。
* As a 報案者, I want **災害種類由系統預設、我不用選**, so that 不必判斷自己遇到的是哪一類災害。
* As a 報案者, I want **拿到一個可追蹤的識別、之後能查進度**, so that 知道有人接手我的求救。

### 志工（接案者）
* As a 志工, I want **以「需求（Task）」為單位承接，而非整個地點**, so that 我能只接我做得到的那一項（例如只送物資、不做破拆）。
* As a 志工, I want **承接清單優先顯示缺口大／優先級高／距離近的 Task**, so that 我的人力流向最需要的地方、不扎堆。

### Team Member（後台代報與處理）
* As a Team Member, I want **替電話進線的民眾代為建立 Ticket（`staff_intake`）並套用較完整的欄位**, so that 後台掌握的資訊比民眾自助報案更完整。
* As a Team Member, I want **處理自家被指派任務、回報進度與現場照片**, so that 後台與現場對同一份事實沒有落差。

### Team Admin（自家責任區）
* As a Team Admin, I want **檢視並管理自家責任區的所有 Ticket/Task**, so that 掌握全局並分派人力。
* As a Team Admin, I want **為需要的建築啟動專業救援模式、要求補齊結構評估**, so that 高風險現場的關鍵情報不遺漏（細節見 prd.md 直立救援）。

### Government（劃區指派）
* As a Government 成員, I want **在地圖拉框把範圍內任務批次指派給某 Team**, so that 不必逐筆操作、快速劃定責任。

### Super Admin（全域治理）
* As a Super Admin, I want **設定/啟動災害種類並決定其預設專業欄位組合**, so that 新災害出現時能即時讓系統承載（積木組裝，見 grill-decisions D2）。
* As a Super Admin, I want **對生命危急任務一鍵啟動最高優先級覆寫（立刻救援）**, so that 立即讓全員看見、不被默默漏接。

### Data Auditor（審查與整理）
* As a Data Auditor, I want **看到 AI 建議的「同地址多筆 Ticket」群組候選並一鍵確認**, so that 快速整理地圖上的重疊標點。
* As a Data Auditor, I want **並排對比 AI 標記的疑似重複任務**, so that 快速合併、保留或拒絕。

## 設計北極星原則（推導 prd.md 時的守則）

1. **報案不卡關**：第一線求救永遠走精簡路徑；專業欄位一律可選、可後補（決策見 grill-decisions D7=C）。
2. **必填依來源分流**：`citizen_report` 極簡、`staff_intake` 標準、`system` 依映射（D4）。
3. **地點與需求分離**：Ticket 管「在哪」、Task 管「要什麼」；指派與接案以 Task 為單位。
4. **一套骨架承載所有災種**：災害差異透過 `disaster_type` 與可選欄位群表現，不為每種災害另造一張表的骨架。
