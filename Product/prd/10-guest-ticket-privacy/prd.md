# Feature PRD — 訪客端工單隱私 (Guest Ticket Privacy)

> **版本：** v0.1 — 草稿（Definition Phase）
> **日期：** 2026-06-29
> **狀態：** 草稿，待產品決策（位置精度、內文揭露、存取門檻三項待拍板）
> **所屬功能：** 公開前台 ／ 跨 08-ticket-management × 04-rbac
> **關聯文件：** `ai-context/decisions-log.md`、`product/prd/04-rbac/prd.md`、`product/prd/08-ticket-management/prd.md`
> **觸發背景：** 後端 `feature/pii-protection` PR（僅遮罩工單 3 個聯絡欄位）的審查發現——訪客端真正的隱私面遠大於聯絡欄位，需獨立定義。

---

## 核心概念：兩個常被混淆的機制

訪客端隱私要靠**兩個正交機制**，缺一不可：

1. **存取控制（Access Control）＝ 這張工單該不該被訪客看到。**
   先決定哪些工單會出現在未登入者的查詢結果裡。這是「鎖門」。
2. **欄位揭露分級（Field Disclosure）＝ 看得到的工單，每個欄位給到什麼程度。**
   對允許訪客看到的工單，逐欄位決定：原文／降精度／摘要／隱藏／遮罩。這是「決定哪些窗戶透明」。

> **關鍵原則：遮罩（masking）擋不住自由文字。**
> 把「欄位」塗黑只對結構化欄位（電話、Email）有效；對 `description`、`title` 這類自由文字，使用者常自己在內文寫了地址、電話、姓名——欄位式遮罩抓不到。因此自由文字欄位對訪客採「**不給原文**」（隱藏或給系統產生的摘要/分類），而非「遮罩」。

**現況基線（`feature/pii-protection` 已實作）：** 僅 `contactName / contactEmail / contactPhone` 三欄對訪客遮罩；其餘欄位（含精確座標、描述、照片、審核註記）對訪客**全部原樣開放**，且 `tickets()` / `ticket()` 不做任何可見性過濾。本 PRD 要補的就是這塊真空。

---

## 使用者情境

* **角色：** 訪客（未登入的一般民眾／潛在惡意第三方），透過公開救災地圖或前台查詢工單。
* **場景：** 災害應變期間，民眾打開公開地圖想了解「附近哪裡有需求、整體災情」；同一個入口，惡意者也能匿名瀏覽。
* **痛點 / 風險：**
  - **實體鎖定**：門牌級精確座標 + 求助處境（獨居、行動不便、家中有待領物資）= 把弱勢者攤開給到府行竊／搶物資／騷擾。
  - **精準詐騙**：`description` 自由文字常含地址、電話、處境、急迫度，足以讓詐騙者冒充救災單位精準行騙。即使聯絡欄位已遮罩，內文照樣洩漏。
  - **二次傷害**：照片可能含人臉、屋內、車牌；審核註記是內部資料。

---

## IDEAL Case

1. 訪客打開公開救災地圖，看到的是**聚合熱區／降精度標記**——能判斷「這一帶有需求、整體災情輕重」，但無法定位到任何單一求助者的家門口。
2. 點開一張公開工單，看到的是**對外安全的摘要**：需求類型、急迫度、概略區域、處理狀態；看不到自由文字原文、精確座標、照片、聯絡資訊原值。
3. 標記為 `restricted` / `internal` 的工單，**完全不出現**在訪客的任何查詢結果中。
4. 想看到完整資訊（精確位置、聯絡方式、內文）→ 需登入且具備對應角色（依 [[04-rbac]] 可見性矩陣）。
5. **結果：** 救災可用性（看得到災情分布）與求助者安全（無法被匿名鎖定）同時成立。

---

## User Story

* As a **求助的災民**, I want **我的精確住址、聯絡方式、處境細節不會被任何未登入者看到**, so that **我不會因為求助而被詐騙、行竊或騷擾**。
* As a **關心災情的一般民眾（訪客）**, I want **看到概略的需求分布與災情輕重**, so that **我能了解狀況或就近提供協助，而不需要、也不該看到個資**。
* As a **平台營運者**, I want **訪客端的資料揭露有明確分級且預設最小揭露**, so that **平台不會因為過度暴露求助者個資而造成傷害與法遵風險**。

## 功能需求

### F1. 訪客存取控制（先於揭露）

* **F1.1** 訪客（`context.user is None`）的 `tickets()` / `ticket()` 只回傳 `visibility = public` 的工單；`restricted`、`internal` 一律**不回傳**（查單筆時等同「查無此單」，不得回 403 暗示其存在）。
* **F1.2** 揭露分級（F2）只套用在「通過 F1.1 的工單」上——存取控制是第一道閘門，欄位揭露是第二道。
* **F1.3** 審核門檻：未通過核實（`verification_status = unverified` 或 `disputed`）的工單是否對訪客顯示，見【開放問題 1】。

### F2. 訪客端欄位揭露分級

對允許訪客看到的工單，逐欄位規格如下：

| 欄位 | 訪客揭露程度 | 機制 | 理由 |
| --- | --- | --- | --- |
| `geometry`（座標） | **降精度**（網格/行政里中心 + 雜訊，或聚合熱區） | 降精度 | 防實體鎖定／導航到府 |
| `description`（求助內文） | **隱藏**，或僅給系統分類／結構化摘要 | 不給原文 | 自由文字夾帶地址/電話/姓名 |
| `title` | **僅給分類化／審核後標題**，不給原始自由文字 | 不給原文 | 同上，標題也可能含 PII |
| `photos` | **隱藏**（除非經審核去識別後才公開） | 隱藏 | 人臉／屋況／車牌 |
| `contactName/Email/Phone` | **遮罩**（沿用現行 PR） | 遮罩 | 已實作；保留 |
| `review_note`（審核註記） | **隱藏** | 隱藏 | 內部審核資料 |
| `verification_status` | 僅給簡化標記（已核實／未核實），不給 `disputed` 等細節 | 收斂 | 避免洩漏審核內情 |
| `created_by`（提交者 UUID） | **隱藏** | 隱藏 | 訪客不需知道提交者身份 |
| `status` / `priority` / `task_type` | 可見 | 原文 | 救災協調需要，無 PII |

* **F2.1** 揭露分級以**欄位層級**實作（延續現行 `MaskForGuests` extension 模式），讓所有回傳工單的路徑自動套用，無需逐 resolver 改。
* **F2.2** 對訪客隱藏的欄位回傳 `null`（型別不變，前台查詢不破），不可回傳塗黑佔位字串以外的可解析殘值。
* **F2.3** 自由文字「摘要／分類」若採 AI 產生，須先過去識別（de-identification）再對外，不得直接回原文片段。

### F3. 位置降精度規格

* **F3.1** 訪客端座標一律不給門牌級精度；降到網格或行政區層級（實際精度見【開放問題 2】）。
* **F3.2** 降精度應在**後端輸出時**完成，不可只在前台視覺模糊（前端模糊無法防止直接打 API 取原值）。
* **F3.3** 公開地圖在高密度區域以**聚合熱區**呈現，而非逐點標記，進一步降低單點可定位性。

### F4. 一致性與防呆

* **F4.1** 訪客端不得存在任何繞過 F1/F2 的路徑：包含 GraphQL 巢狀 resolver、mutation 回傳、REST 端點、匯出/報表。新增任何回傳工單的入口都必須套用同一套揭露分級。
* **F4.2** 移除或封存未接入遮罩的重複型別／死碼（後端 `app/graphql/{types,queries,mutations}.py` 中未遮罩的舊 `TicketType`），避免日後誤接造成裸奔外洩。
* **F4.3** 本分級規則須回填進 [[04-rbac]] 資料可見性矩陣，新增「訪客（未登入）」一欄（呼應 04-rbac README 既有待辦）。

## 成功驗收標準

- [ ] 訪客查詢 `restricted` / `internal` 工單時，列表不含、單筆回「查無」，且回應不洩漏其存在。
- [ ] 訪客取得的任一工單，`description`、`title` 原始自由文字、`photos`、`review_note`、`created_by` 皆不可得（為 `null` 或安全摘要）。
- [ ] 訪客取得的 `geometry` 精度不高於約定網格層級；以原值反查無法定位到單一門牌。
- [ ] 直接對後端 API（非經前端）發出匿名請求，仍無法取得上述受保護欄位的原值（驗證非僅前端模糊）。
- [ ] 同一筆工單，登入且具權限者可取得完整原值（揭露分級僅作用於訪客，不影響授權使用者）。
- [ ] 自動化測試涵蓋：列表、單筆、巢狀、mutation 回傳四條路徑的訪客揭露行為，以及死碼型別保持未接入。

## 開放問題

1. **未核實工單是否對訪客顯示？** `unverified` / `disputed` 的求助若直接公開，可能放大假需求或詐騙誘餌；但若全擋，緊急初期（尚未審核）的真實需求就看不到。需在「即時可用性 vs 假訊息風險」間拍板門檻。
2. **位置降精度的實際層級？** 行政里中心、固定網格（如 100m / 250m）、或可變半徑——精度越低越安全，但救災媒合也越難就近指派。需與 06-map-decision-support 一起定，可能對「訪客」與「登入志工」採不同精度。
3. **照片是否提供「審核去識別後公開」路徑，或一律對訪客隱藏？** 若要公開（提升災情可信度），需定義去識別流程與審核責任歸屬；否則預設一律隱藏。
