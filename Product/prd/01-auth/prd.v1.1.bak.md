## 使用者情境

* **角色：** 前台一般使用者（市民、志工）、後台管理人員（Super Admin、Data Auditor 等）
* **場景：** 使用者首次或每次造訪平台時，需通過身份驗證才能存取對應功能。後台人員在後台工作台處理任務單據前須登入。
* **痛點 / 觸發點：** 不同角色的使用情境差異大——一般民眾習慣社群帳號登入，後台人員需要企業級 SSO 與 RBAC 整合，兩套流程若沒有清楚分離，容易造成權限混淆或登入摩擦。

---

## IDEAL Case

1. 前台使用者點擊「登入」，看到 Email / SMS / Google / Line 四種選項，一鍵選擇慣用方式。
2. 驗證完成後立即進入個人首頁，無額外跳轉或確認步驟。
3. 後台管理人員透過究平安 SSO 登入，系統自動識別 RBAC 角色後直接導向管理後台首頁，不需要再選擇角色。
4. **結果：** 兩類使用者都能在 30 秒內完成登入，且進入的介面與權限與角色完全吻合。

---

## User Story

* As a **市民或志工**，I want **用 Line 或 Google 帳號一鍵登入**，so that **不需要記住額外的帳號密碼**。
* As a **市民或志工**，I want **用手機號碼收 SMS 驗證碼登入**，so that **在沒有社群帳號的情況下也能使用平台**。
* As a **後台管理人員**，I want **透過究平安 SSO 登入後自動取得對應權限**，so that **不需要手動切換角色，能直接開始工作**。

## 功能需求

### 前台使用者登入

* **自有帳號系統**
  * Email 登入
  * 手機簡訊（SMS）驗證碼登入
* **第三方登入**
  * Google (Gmail) OAuth 登入
  * Line OAuth 登入

### 後台管理人員登入

* 使用**究平安 (SSO)** 系統進行身份驗證。
* 登入後自動取得基於角色存取控制（RBAC）的分級權限。
* 驗證成功後導向管理後台首頁。

## 帳號識別與連結（v1.1 拆細）

> 既有驗收標準只說「第三方登入帳號自動建立」，但沒回答「同一人用多種方式登入是否＝同一帳號」。這是身份系統最常見的帳號接管漏洞來源，需先定義清楚。

* **內部主鍵**：平台以一個穩定的 `internal_user_id (UUID)` 為帳號主體，Google / Line / SMS / Email 各為掛在其下的 **identity（provider + provider_uid）**。
* **首次登入**：找不到任何相符 identity → 建立新帳號（沿用既有驗收標準）。
* 🟡 **建議（帳號合併策略）**：偵測到「相同且**已驗證**的 Email 或手機」時，**不自動靜默合併**，而是要求使用者「用既有方式登入一次」確認後才連結（業界稱 verified-linking，Auth0 / Firebase 主流作法，避免 pre-account-takeover）。
* 🟡 **待確認（Line 無 Email）**：Line 不保證回傳 Email（使用者可拒授權）。建議：Line 帳號預設為獨立帳號，之後於 [[03-user-settings]] 設定頁「手動連結其他登入方式」；或以手機號碼當輔助識別。
* **帳號枚舉防護**：登入 / OTP 失敗時，「不存在的帳號」與「密碼/驗證碼錯誤」回傳**相同**的通用錯誤訊息。

## OTP 與防濫用規格（v1.1 拆細，🟡 建議值）

> SMS / Email OTP 是最常被攻擊的環節（簡訊轟炸、暴力猜碼、SMS pumping 計費詐騙）。下列為建議預設值，供確認後鎖定。

| 項目 | 🟡 建議值 | 目的 |
|------|------|------|
| 驗證碼長度 | 6 位數字 | NIST 下限 |
| 有效期 | SMS 5 分鐘 / Email 10 分鐘 | 平衡體驗與風險 |
| 同碼錯誤上限 | 3 次即作廢 | 防暴力猜碼 |
| 重送間隔 | ≥ 60 秒 | 防簡訊轟炸 |
| 單號碼頻率 | 每小時 ≤ 5 則、每日 ≤ 10 則 | 防成本攻擊與騷擾 |
| 單 IP 頻率 | per-IP 限流 + 異常上 CAPTCHA | 防自動化 |
| 境外號碼 | 🟡 建議限制非 `+886` 號段需額外驗證 | 防 SMS pumping |

## Session 與權限生效（v1.1 拆細）

* **Token**：短期 access token + 滾動 refresh token；**後台高權限帳號的 access token 更短**。
* 🟡 **建議**：前台可「記住我」30 天；**後台高權限閒置逾 30–60 分鐘要求重新驗證**。
* **多裝置**：允許多 session 並存；[[03-user-settings]] 應提供「登出所有其他裝置」。
* **RBAC 變更生效**：與 [[04-rbac]] 一致——靠短 access token 讓新權限在下次 token 刷新時自然生效，**不強制登出**。
* 🟡 **建議**：後台 SSO 登出連動究平安 **Single Logout**，避免「平台登出但 SSO 仍在」。

## 異常場景（v1.1 新增）

> 標示「⛔ 系統阻擋」為前後端應強制的硬規則；「🟡 待確認」者列入下方開放問題。

| 編號 | 場景 | 處理建議 |
|------|------|----------|
| **A1** | 同一人先用 Line 註冊（一般使用者），日後又用相同手機 SMS 登入 | 走帳號合併策略（verified-linking），提示連結而非建立第二帳號。 |
| **A2** | Google/Line 授權回傳但未提供 Email | 仍可建帳號（以 provider_uid 為識別），Email 留空，於設定頁補登。 |
| **A3** | 連續登入失敗 | 🟡 建議採指數退避（throttling）+ 多次失敗上 CAPTCHA，**不採永久硬鎖**（永久鎖定本身是 DoS 面，見研究檔 §4）。 |
| **A4** | 後台 SSO 登入成功，但平台查無此人 / 無對應角色 | 🟡 建議 JIT 佈建：建帳號但**給最低權限**並落入「待 Super Admin 指派」，同時通知 Super Admin，**不直接拒絕**（避免應變期卡人）。 |
| **A5** | SSO 端帳號已被停用 | 平台在下次 token 刷新驗證時同步失效。 |
| **A6** | 災害期間究平安 SSO 服務中斷，後台人員進不來 | ⛔/🟡 待確認：是否保留至少 1 組平台原生緊急 Super Admin 帳號（break-glass），與 [[04-rbac]] break-glass 討論一致。 |
| **A7** | 第三方 OAuth 回呼失敗 / 使用者中途取消授權 | 回到登入頁並顯示明確可重試訊息，不留下半建立的殘帳號。 |
| **A8** | 一般使用者升等為後台角色後，原社群登入仍可用 | 同一 `internal_user_id`，登入方式不變、RBAC 改變即可（與 [[03-user-settings]] 升等流程銜接）。 |

## 成功驗收標準

- [ ] 前台使用者可透過 Email、SMS、Google、Line 四種方式完成登入。
- [ ] 後台人員透過 SSO 登入後，系統自動對應 RBAC 角色，無須手動選擇。
- [ ] 登入流程從點擊到進入首頁不超過 30 秒（正常網路環境）。
- [ ] 登入失敗時顯示明確的錯誤訊息，說明失敗原因。
- [ ] 第三方登入（Google / Line）在帳號未曾使用過時，自動完成帳號建立。
- [ ] 同一人以多種方式登入時，依帳號合併策略不會產生重複帳號（或合併需經二次驗證）。
- [ ] OTP 達錯誤上限即作廢、重送有間隔限制、單號碼/單 IP 有頻率上限。
- [ ] 登入失敗訊息不洩漏帳號是否存在（防枚舉）。
- [ ] 後台 SSO 查無對應角色時不直接拒絕，而是給最低權限並通知 Super Admin。

## 開放問題（v1.1 新增，待確認）

- [ ] 帳號合併採 verified-linking（已驗證 Email/手機相符才提示合併、需二次驗證）？
- [ ] Line 無 Email 時：獨立帳號 + 手動連結，還是以手機當輔助主鍵？
- [ ] OTP 參數採本文件建議值（6 碼 / 5 分鐘 / 3 次 / 60 秒 / 每日 10 則）？
- [ ] 是否限制非 +886 號段需額外驗證以防 SMS pumping？
- [ ] 後台 SSO 是否支援 JIT 佈建？未對應角色者給最小權限 + 待指派？
- [ ] 究平安 SSO 中斷時是否保留 break-glass 緊急原生帳號？
- [ ] 後台高權限是否採 30–60 分閒置逾時重新驗證？
