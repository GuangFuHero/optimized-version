## 這頁在做什麼

系統（後端快層）發現兩張任務單或兩個站點可能在講同一件事，就產生一張**配對卡**。審核員在這一頁兩張並排比對，決定：

| | 任務單 | 站點 |
|---|---|---|
| 合併 | ✅ 兩張合成一張 | ❌ 這一版不能合併（後端 ADR-377 回 422） |
| 確認重複（只記判定） | — | ✅ `confirm`，兩個站點都不會變 |
| 不是重複 | ✅ `reject` | ✅ `reject` |

🔒 DUP-BE-420：**一次處理一對**（同後端配對卡）。同一張單上的兩筆需求不會出現在這裡（DUP-BE-425）。

## 畫面組成

```
清單畫面（ListView）
├─ 分頁：任務單（N）／站點（N）        ← 待處理的數量
├─ 待處理／已處理 切換
├─ 排序：相似度高的在前／最新建立的在前
└─ 一對一列（GroupRow）：相似度 · A、B 兩張的需求名稱 · 單位 · 最早建立時間＋前後差多久

比對畫面（CompareView，網址帶 #<配對 id>，瀏覽器上一頁回清單）
├─ 頂列：回清單 · 相似度 · 上一對／下一對
├─ 為什麼可能重複（signals）· 只看有差異的欄位
├─ 比對表（CompareTable）：欄位名稱固定在左，A／B 表頭固定在上
│   ├─ 基本資料：單位·建立者、建立時間（最早／晚多久）、最後修改
│   ├─ 合併後的任務單：每一列挑一個值（標題、描述、聯絡人、優先級、地址、災害欄位）
│   ├─ 重複的需求 → 合併成一筆：每一列挑一個值；數量可以自己填
│   └─ 其他需求與照片：兩張的全部列成勾選
└─ 底部動作列：不是重複 · 合併後會發生什麼 · 合併

確認視窗（ConfirmDialog）
├─ 合併：合併後那張任務單的預覽（MergePreview）＋送出後會發生＋備註
└─ 不是重複／確認重複：送出後會發生＋備註
```

## 核心規則

### 合併任務單：使用者看到的是「兩張合成一張」

🔒 **DUP-BE-430**：畫面上**不出現**「保留哪一張」「整張取消」「搬到 A」。使用者只關心合併出來的那張單對不對。

- 每個欄位挑一個值
- 兩張單上的**其他需求**、**照片**全部列成勾選；勾的放進合併後的單，沒勾的取消。**預設全勾**（🚨 預設勾比較不會漏）
- 確認視窗只給看結果（DUP-BE-413），**不標**「這個值來自哪一張」

### 但後端一定要 primary：前端自己決定

🔒 **DUP-BE-431**：resolve 要帶 `primary`（主要單，另一張由後端整張取消，ADR-371）。前端照下面決定，**不給使用者看**：

1. 後端這一版**不能改地址**（ADR-367），所以**使用者挑哪一張的地址，那一張就是 primary**
2. 兩張地址一樣 → 重複那筆需求**有志工承接的那張**，其次**最早建立的**（`ddPrimary()`）

挑了另一張的地址，其他欄位**不會**跟著跳（每一列的預設值是一開始就決定好的，`picksFor()`）。

### 欄位：有什麼列什麼

🔒 **DUP-BE-410**：比對表的欄位**不可以寫死**。

| 來源 | 例子 | 後端 |
|---|---|---|
| 單本身的欄 | 標題、描述、聯絡人、優先級、地址 | `TicketForReview` 的 `title`、`description`、`contact_*`、`priority` |
| 需求本身的欄 | 需求種類、需求名稱、數量 | `tasks[].task_type`、`task_name`、`quantity` |
| 需求的設定欄位 | 物品名稱、清理類型、需要工具… | `tasks[].properties`；名稱看 `task_property_config.label` |
| 災害欄位 | 積水深度、電力、聯外道路… | `disaster_details`；名稱看 `ticket_property_config.label` |

- 名稱用設定的 `label`；沒有 label 或設定被刪了 → 顯示 `property_name`（同後端 `property_config.py`）
- 順序照 `sort_order`；設定裡沒有的排最後
- 停用的欄位，舊資料有值照樣列出
- **兩張都沒填的欄位不列**，表格下面寫一句「兩張都沒填、所以沒列出來：…」
- 預設值：用 primary 那張的；那張沒填、另一張有填 → 預設用另一張的（不然那個值會跟著另一張被取消）

原型的實作在 `dd-data.js` 的 `ddFieldsFor()`；欄位設定從 `js/admin/settings/st-data.js`（設定頁）讀。

### 值只能挑，數量可以填

- 🔒 DUP-BE-404：值只能從兩張挑，不能自己打新內容
- 🔒 DUP-BE-422：**數量例外，可以自己填**。旁邊提示「兩張加起來是 N」，但🚨**不預設加總**（同一件事報兩次，加總會變兩倍）
- 🔒 數量**不能少於合併後的承接人數**（後端 ADR-370）。少於 → 欄位下方紅字、確認視窗擋下不能送出。搜救（rescue）以外沒填也擋

### 志工

🔒 DUP-BE-423：重複那筆需求**兩邊已承接的志工都留在合併後的需求**繼續承接（後端 ADR-369），不是釋出。勾進來的其他需求，志工跟著。沒勾的需求上的志工收到取消通知。通知由後端發（Spec 028 §6）。

### 送出

- 🔒 DUP-BE-401：送出後**不能復原、不能拆回**（ADR-376）。沒有「五秒反悔」
- 🔒 DUP-BE-402：三個按鈕都先跳確認視窗，按「確認…，送出」才寫入
- 🔒 DUP-BE-427：確認視窗有**備註**（選填，≤1000 字 → `note`）
- 🔒 打開後有一張被改過 → 送出時擋下，提示重新載入（後端 `expected_versions` 對不上回 **409**，ADR-374）。示範：`?demo=1` 的「光復國小 毛毯」那一對
- 🚨 處理完自動跳到下一對待處理；最後一對處理完回清單

### 清單

- 🔒 DUP-BE-411：**不顯示「來源」**（建立時仍要建立／批次匯入／背景掃描），也不能用來源篩選
- 🔒 DUP-BE-412：兩張**依建立時間排，A 最早**。清單寫「最早 MM/DD HH:mm」＋「前後差多久」（同時建立就寫「同時建立」）；表頭寫「最早」或「晚 N 小時 M 分」；基本資料寫完整時間（🚨 三處怎麼放設計端先定）
- 🔒 文案一律寫「**可能**重複」

## 送出時怎麼轉成 resolve 的 request

使用者的操作 → `POST /admin/duplicate-pairs/{uuid}/resolve`：

| 使用者做了什麼 | request |
|---|---|
| 地址挑了哪一張（或 `ddPrimary()`） | `primary: "low" \| "high"` |
| 打開比對畫面時拿到的兩張單 `version` | `expected_versions` |
| 單本身的欄位挑了另一張的值 | `ticket: { title, description, priority, contact_name, contact_phone, contact_email }`（只帶有改的） |
| 重複那筆需求 | `primary_tasks` 裡 primary 的重複需求：`action: "keep"`、`absorb: [另一張的重複需求]`、`values: { task_name, task_description, quantity }`、`properties`（挑完的每一個細項） |
| primary 的其他需求：勾／沒勾 | `primary_tasks`：`keep`／`cancel` |
| 另一張的其他需求：勾／沒勾 | `secondary_tasks`：`move`／`cancel` |
| 照片：勾／沒勾 | `photos`：`keep`／`cancel`（兩張的每一張都要列） |
| 災害欄位 | `disaster_details`：挑完的**完整**一份（另一張有答案時必填） |
| 備註 | `note` |

例：大進街 12 號被報了兩次（`?demo=1` 的第一對）

```
A T-2101  清淤人力 ×6（3 人承接）＋ 推車 ×2          照片 2 張
B T-2108  清泥人力 ×4（1 人承接）＋ 飲用水 ×2 ＋ 尿布 ×1   照片 1 張
地址相同 → primary = A（重複需求有人承接、又最早）
使用者：聯絡人挑 B、數量填 8、尿布沒勾、照片「門口」沒勾
```

```json
{
  "primary": "<A 那一邊>",
  "expected_versions": { "low": "…", "high": "…" },
  "ticket": { "contact_name": "陳太太", "contact_phone": "0921-…" },
  "primary_tasks": [
    { "task": "<A 清淤人力>", "action": "keep", "absorb": ["<B 清泥人力>"], "values": { "quantity": 8 }, "properties": [ … ] },
    { "task": "<A 推車>", "action": "keep" }
  ],
  "secondary_tasks": [
    { "task": "<B 飲用水>", "action": "move" },
    { "task": "<B 尿布>", "action": "cancel" }
  ],
  "photos": [
    { "photo": "<一樓客廳>", "action": "keep" },
    { "photo": "<門口>", "action": "cancel" },
    { "photo": "<廚房>", "action": "keep" }
  ],
  "note": "已電話確認是同一戶"
}
```

原型沒有真的組這個 request（`dd-app.jsx` 的 `merge()` 只改本地資料），註解寫在 `merge()` 開頭。

## 權限

| | 超級管理員 | 政府 | NGO 管理員 | NGO 成員 | 資料檢核員 |
|---|:-:|:-:|:-:|:-:|:-:|
| 側欄看得到「重複審核」 | ✅ | ✅* | ✅ | — | ✅ |
| 看得到哪些 | 全部 | 含自己團隊的 | 含自己團隊的 | — | 全部 |
| 能處理 | ✅ | 兩張都是自己團隊的 | 兩張都是自己團隊的 | — | ✅ |

\* 政府看得到是因為吳政憲是政府隊的**管理員**，不是因為他是政府。
跨單位或含未指派單位的：團隊管理員只能看，動作列換成「你只能查看這一對」。

⚠️ **DUP-BE-428：後端目前只開給超級管理員、資料檢核員**（`ai_duplicate.view`／`ai_duplicate.review` 只 grant 這兩個角色，見 `alembic/versions/1649d30b0122_ai_duplicate_grants.py`）。🔒 設計端確認**團隊管理員要能處理** → **請後端開給團隊管理員**，scope ＝兩張都屬於自己團隊。後端開之前，前端照後端回的 capability 顯示即可，不要自己判斷角色。

## 空白狀態

| 情況 | 畫面 |
|---|---|
| 待處理是空的 | 圖示＋「目前沒有待處理的可能重複」＋說明配對從哪來（建單或改單時很像、CSV 匯入撞到、被提醒後仍選擇送出）。**沒有按鈕**（這頁不能自己建配對） |
| 已處理是空的 | 「在待處理按下合併或不是重複之後，會留在這裡，方便事後查是誰決定的」 |
| 站點分頁 | 上方多一句「站點這一版還不能合併…」 |
| 身份不能用這頁 | 「你目前的身份不能使用 重複審核」＋可以從右上角切換身份 |

## 實作陷阱

- **不要讓使用者看到 primary。** 標題、預覽、送出後的說明都不要寫「保留 A／B 整張取消」。已處理的紀錄可以寫單號（給事後查）。
- **欄位不要寫死。** 新的需求類型、新的災害欄位，設定頁一加就要出現在比對表。
- **挑地址會換 primary，但不要讓其他欄位跟著跳。** 每一列的預設值在打開時就定好。
- **數量輸入框**：原型踩過的坑 —— 把輸入框寫成「每次 render 都重新定義的元件」會讓它每打一個字就掉焦點（`dd-app.jsx` 的 `qtyTypeIn()` 用函式呼叫就是這個原因）。
- **確認視窗開著時換到別的一對**（瀏覽器上一頁、上一對／下一對）要把視窗關掉，不然會拿新那一對去算。
- **409**：送出拿到 409 就提示重新載入，不要自動重送。
