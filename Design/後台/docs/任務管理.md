# 任務管理（Ticket Management）

> 原型：`Design/後台/任務管理 Ticket Management.html`
> 程式：`js/admin/ticket/*`、外殼轉接 `js/admin/shell/tk-shell.jsx`
> 正式版：`Frontend/apps/demo/src/app/admin/tickets/` ＋ `Frontend/libs/modules/src/ticket/`
> 正典：`TM-FEAT-001` 動態欄位、`TM-FEAT-008` History、`TM-FEAT-009` 欄位設定；規則編號 `TM-*`／`AC-VS-*` 見程式註解

## 這頁在做什麼

處理「某個地點需要什麼」。一張**任務單**＝一個地點；一個地點底下可以有好幾筆**需求**（要 10 個清淤人力、200 箱水…）；志工或單位**承接**的是需求，不是整張單。

```
Ticket 任務單（地點：地址＋地標座標）
 └─ Task 需求（種類 搜救/人力/物資、名稱、數量、狀態）
     └─ 承接（誰、接了幾個、什麼時候）
```

後台人員在這裡：看全部的單、建單（代民眾登錄）、把單指派給一個單位、單位管理員再把需求派給隊員、看承接進度與完整歷史。

## 核心規則

- 🔒 **任務單狀態是推導的，後台不能手改**（`tkStatus(t)`）：
  所有需求都「已滿足」→ 已完成；有人承接或有需求進行中 → 處理中；否則 → 待處理。
  「已取消」（建立者在前台撤案）與「已封存」（系統自動）維持原值、唯讀。
- **需求狀態**：待承接 `pending` → 進行中 `in_progress` → 已滿足 `fulfilled`；或已取消 `canceled`。詳情裡可用下拉調整。
- **優先級四級**：生命危急 `critical`／緊急 `high`／一般 `medium`／低 `low`。
  只有「生命危急」用實心紅；SLA 提醒：生命危急 30 分鐘黃、60 分鐘紅；緊急 120／240 分鐘（`TK_PRIORITY.warnMin/overMin`）。
- **範圍切換**（AC-VS-104）：目前身份屬於某個團隊的人（NGO，以及屬於政府隊的政府人員）預設看「我的單位」，可切「全部單位」，但別隊的單在「全部」裡是**唯讀**。超級管理員與資料檢核員恆為全部。
- **圖片只存連結**，平台不存圖。上傳教學指向 duk.tw（`js/shared/wg-photos.jsx` 的 `TK_UPLOAD_HOST`，前後台共用）。🔒 移除圖片時，歷史要記**原網址**（TM-IMG-143）。
- **歷史**（TM-FEAT-008）：每張單都有時間軸，新到舊；至少有一筆「建立任務單」。操作者記**寫入當下的姓名快照**，帳號刪了也讀得到名字（TM-RH-105）；爬蟲建立的單有專屬徽章（TM-RH-106）；欄位事後停用，歷史仍完整保留（TM-RH-107）。
- **動態欄位跟著災害類型走**（TM-FEAT-001）：例如水災有「積水深度、水位趨勢」，土石流有「掩埋範圍」。🚨 目前的欄位與選項是版型示意，要由權責單位提供正式清單。
- 自動封存天數唯讀顯示，實際值在設定頁（`TK_SETTINGS.archiveDays`）。

## 新增地點（2026-10-25）

工具列「新增地點」→ 表單由上到下：

1. **位置（必填）**：地圖點那棟建築，可拖大頭針；點下去自動拉近到 17 級。**不自動抓 GPS**（後台人員多半不在現場）。
2. **地址**：大頭針放下後呼叫一次反查門牌，查到就帶入（「已確認門牌」）；人改過＝「未確認門牌」＋「改回查到的」鈕；500 公尺內查不到＝請自己填，**仍可建立**。
3. **名稱（必填）**：最多 100 字，側欄與前台顯示這個（例：宏福苑 A 座）。
4. **地上 1–200 層、地下 0–20 層**。🔒 **每棟自動加上頂樓 RF**（後端 ADR-310：淹水時人會往頂樓跑），管理員不填、刪不掉。
5. 大頭針 30 公尺內已有地點 → 黃色提醒（🚨 30 公尺是設計端定的；只提醒不擋）。

🔒 車廂、自訂分區是**下一階段**（後端只有樓層＋每層區域 `floor_areas`），這版只做樓層。

| 原型 | 後端 | 備註 |
|---|---|---|
| `lat`, `lng` | `geometry`（GeoJSON Point，**必填**） | `[lng, lat]` 順序 |
| `alias`（畫面叫「名稱」） | `name`（1–100 字，必填） | |
| `address` ＋ `addressStatus` | `secondaryLocation { fullAddress, addressToken }` → `normalizationStatus` verified／unverified | 不可帶棟／樓／室 |
| `floorsAbove`, `floorsBelow` | `floorsAboveGround`（1–200）, `floorsBelowGround`（0–20） | 樓層標籤後端推算：RF、nF…1F、B1…Bn |
| — | `floorAreas` | 每層再分區；原型未做 |

- 地址反查：`reverseGeocode(lat, lng)`（**只在放下／拖完大頭針時打一次，不在拖曳中、不在打字時打**；每人每分鐘 30 次）。原型的 `mockReverseGeocode` 只是假的，⚠️ **交付版沒有示範資料，所以永遠回「查不到」**。完整規則：`Backend/Spec/027-address-normalization/frontend-guide.md`，程式碼註解 BM-1〜4、BM-11〜15。
- 權限：後端要 `work_zone.add` ＋ **政府隊**；原型用 `tk.can.activate`（超管／政府）。無權限者工具列是唯讀的「已新增的地點」。
- 任務單歸到哪一棟：正式版建單時帶 `buildingMapUuid`（點位與地址用那棟的）；原型前台仍用地址字串比對。任務單樓層寫「頂樓／屋頂／RF」會歸到 RF。
- 排序：原型照「小數字在上」B1、1F…nF、**RF 排最後**；後端回傳是 RF 在最前，畫面可自己排。

## 實作陷阱

- **承接記在需求上，不是任務單上。** 舊原型曾把前台所有承接塞進 `tasks[0]`，造成「志工送的是水，後台卻顯示清淤有人來了」（2026-09-04 修掉）。正式版 `task_assignments` 本來就是 per task，照著做就不會錯。
- **不要讓後台手改任務單狀態。** 它是推導值，手改會跟需求進度對不起來。
- 座標順序：Leaflet 是 `[lat, lng]`，GeoJSON 是 `[lng, lat]`。原型全部走 `tkCoord()` 一個出口，正式版也建議集中一處轉換。
- 建單與編輯都要**保存地標**。（原型 10-16 之前漏存，已修。）
- 新建的單 `region` 是空的，篩選選項要濾掉空值，否則會出現一個空白的行政區選項。
- 兩種空白狀態要分開做（見上表）；「調整篩選再試」不能出現在一筆資料都沒有的時候。
